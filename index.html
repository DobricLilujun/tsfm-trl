    tsfm-trl¶

    Time-series foundation models behind one API — and an honest map of what each architecture can actually do in a given environment.

    tsfm-trl is first a benchmark and compatibility harness: 46 open TSFM checkpoints (Chronos family, TimesFM 2.x/2.5/3.0, Moirai 1.1/2.0/MoE, MOMENT, TTM, Toto, Time-MoE, Sundial, Kronos, TiRex, Kairos, Timestral, Hirondel, t0, FlowState, VisionTS, Aurora, Yug, plus statistical baselines) loaded through one adapter contract, then driven through the same set of tasks. Post-training (fine-tune, probing, reward/RL) sits on top of that contract — it is a capability gate, not a claim that any model got better.

    The two claims this library keeps apart¶

    question produced by can be quoted as
    compatibility does this architecture load, forecast, emit quantiles, embed, classify, detect anomalies, take post-training — in this environment? tsfm-trl doctor → measured matrix yes, with the machine and env in the row
    effectiveness how accurate is it? tsfm-trl evaluate → RMSE/MASE/CRPS/WQL/coverage yes, per the protocol
    capability smoke does a training step run at all? doctor's fine-tune/reward columns only as "it runs", never as "it helps"

    Mixing the third into the first is the most common way a TSFM table becomes misleading, so the matrix labels it separately and the fine-tune cell says what its numbers mean.

    Quick tour¶

    pip install -e .                       # core only; per-family venvs: scripts/make_envs.sh

tsfm-trl list --tier A                 # what the registry knows about
tsfm-trl forecast --model chronos-t5-small --horizon 21 --md
tsfm-trl evaluate --model toto-2-22m --horizons 21,63,126 --max-windows 32

tsfm-trl classify --model moirai-2.0-R-small --label dir5 --routes probe,head,native
tsfm-trl reward  --model chronos-t5-small --steps 48 --peft lora --mode auto

tsfm-trl doctor --all-envs --json reports/matrix.json      # the compatibility matrix
tsfm-trl doctor --merge reports/*.json --md COMPATIBILITY.md

    Measured compatibility (2026-11-21, 46 models, two machines)¶

    task ok declined by the model failed not checked
    load 45 0 1 0
    forecast / predict 44 0 1 1
    quantiles 35 9 0 2
    embed 44 0 1 1
    classify 44 0 1 1
    anomaly 44 1 0 1
    reward / RL 30 15 0 1
    fine-tune (capability) 29 9 0 8

    The two red cells are named, not averaged away: VisionTS++ (the Hub repo ships .ckpt weights only, the upstream package is not installable as a package) and TiRex-2 (the vendor's Triton mLSTM scan kernel compiles at import and then fails at runtime on CUDA 13 / sm100, and the native fallback's JIT-built extension does not import — see known issues).

    declined means the model or its public package has no path for that task here (TimesFM's build is inference-only, Moirai 1.1's forward samples instead of returning differentiable quantiles). failed means something was attempted and broke, with the reason captured in the row. History says to doubt failed before believing declined: three "the model cannot be fine-tuned" verdicts in this project turned out to be our bugs.

    Which post-training path each architecture exposes¶

    path models requirement
    grpo 2 (Chronos-T5 small/base) token log-probabilities over its own sampled paths
    rft 18 can sample candidate paths; no log-prob needed
    descent 5 differentiable quantile head
    descent·pt 5 differentiable point head only
    — 15 no trainable path in the public build

    GRPO here is hand-written (~435 lines in tsfm_trl/training/reward.py), with no RL library dependency; only two architectures expose the token log-probs that true GRPO needs, which is a property of the vendor builds and not something the harness papers over. Details in RL / reward API and Reward & RL paths.
